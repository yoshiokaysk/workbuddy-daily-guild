# 第 2 章 建立正确的协作预期

很多人用 WorkBuddy 的挫败感，不是来自产品能力，而是来自预期错位：要么把它当搜索引擎，问一句就想要标准答案；要么把它当全自动员工，扔一句话就期待成品。

这一章把预期校准到能出活的位置。

## 核心分工：人定标准，AI 执行

记住这条分工线：

| 环节 | 谁负责 | 具体含义 |
| --- | --- | --- |
| 定目标 | 你 | 要什么结果，为什么做 |
| 定标准 | 你 | 什么算合格，格式、长度、语气 |
| 给输入 | 你 | 原始材料、背景、限制条件 |
| 出初稿 | 它 | 按你的要求生成第一版 |
| 做判断 | 你 | 判断能不能用，哪里要改 |
| 定稿 | 你 | 最终负责 |

凡是越过这条线的用法，都会付出代价。比如让它"自己判断哪个方案好"，你省了十分钟，但可能要花一小时发现它判断错了。

## 三种典型错位

### 错位一：当搜索引擎用

**表现**：问"怎么提高会议效率"，得到一段正确但没用的通用建议。

**原因**：问题里没有你的具体情境。它只能给平均值。

**修正**：把你的场景写进去。

```text
别这样：
怎么提高会议效率？

要这样：
我每周主持 3 场产品评审会，每场 60 分钟，经常后半段变成闲聊。
请给出 5 个具体的控场动作，每个动作说明在什么时机说哪句话。
不要泛泛讲"提前发议程"这类大家都知道的建议。
```

### 错位二：当全自动员工用

**表现**：扔一句"帮我做个季度汇报"，然后期待直接能交。

**原因**：你没给数据、没给口径、没给格式，它只能编一个框架。

**修正**：把"成品需要什么"拆开给。

```text
目标：做一份季度汇报的正文初稿
输入：[本季度 4 项关键数据、3 个已完成项目、2 个延期项目及原因]
输出：结构为「总体结论 / 关键数据 / 完成事项 / 问题与下季度计划」，
      总字数 800 字，语气客观
限制：数据只用我给的，不要编造；延期原因按我给的原话写
```

### 错位三：当 oracle 用

**表现**：问"这个项目该不该做"，把重大决策交给它。

**原因**：决策需要的隐含信息（团队状态、老板偏好、机会成本）它都不知道。

**修正**：让它做分析，你做决定。

```text
目标：帮我分析"是否启动 B 项目"
背景：[团队现有 5 人，A 项目占 3 人，B 预计需要 2 人；Q3 必须交付 A]
输出：列出启动 / 不启动 / 延后三种选择的利弊，每种列出最关键 3 条
限制：只做分析，不要给"建议选 X"的结论
```

## 接受"初稿思维"

把 WorkBuddy 的输出一律当**初稿**，你的工作从"从零写"变成"改稿"。这是效率提升的真正来源。

改稿比从零写快，前提是：

1. **初稿方向对**——目标、格式、限制说清楚了，方向就不会偏。
2. **你知道好稿长什么样**——你心里有标准，才能快速判断。
3. **你愿意改**——期待"一次到位"的人，往往第一次就失望。

一个现实的比例：一份 1000 字的周报，说清楚要求后它给出 800 字左右的可用初稿，你花 5–10 分钟补数据、调语气、加判断，就能交。这比你自己盯着空白文档半小时强。

## 遇到"答非所问"时的正确处理

不要立刻重写整个提示词。按顺序排查：

1. **是不是目标没说清？** 它理解的任务和你想要的不一样 → 补一句"我要的是 X，不是 Y"。
2. **是不是缺少输入？** 它没拿到关键材料 → 把材料补上，而不是继续追问。
3. **是不是限制缺失？** 它给了你不要的东西 → 明确"不要做 X"。
4. **是不是任务太大？** 一次塞了太多要求 → 拆成两次，先完成第一部分。

示例：

```text
上一轮它给了很长的背景介绍，但我要的是待办清单。
请重做：只输出待办表格，不要任何背景说明，
表格列为「事项 / 负责人 / 截止」，不超过 5 行。
```

## 一句可复用的自检话术

每次下发任务前，在心里问一句：

> "如果交给一个刚入职、很认真但不了解我们情况的同事，这段话够他做出我要的东西吗？"

如果答案是"不够"，补信息，别急着发。

## 小结

- 分工线：你定目标、标准、输入、判断；它出初稿、做执行。
- 三种错位：当搜索引擎、当全自动员工、当决策oracle——都要用"给场景、给输入、给限制"来修正。
- 接受初稿思维：效率来自"改稿比写稿快"，不来自"一次到位"。
- 答非所问时按顺序排查目标、输入、限制、任务粒度，而不是推倒重来。
