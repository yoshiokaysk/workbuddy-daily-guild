# 用 WorkBuddy 驱动 GuanCLI 完成 ETL 与 BI 看板开发

这是一次 BI 交付项目的复盘。我们做了一件事：把 WorkBuddy 当成"总调度"，让它调用观远的命令行工具套件，用自然语言完成从数据加工（ETL）到看板生成的全过程。

这篇文章按"做成了什么、怎么做到的、踩了哪些坑、哪些经验可复用"来写。重点不在"某个命令怎么敲"，而在"人和 AI 怎么分工、风险怎么控制、口径怎么校验"——这些才是这类项目真正难的地方。

## 一句话成果

> 用约两周时间，交付了一个sales 经营分析场景的 ETL 流程和配套看板；整个过程以自然语言驱动为主，人负责定口径、做确认、验结果，AI 负责读结构、改草稿、生成页面。

## 背景：为什么要这么做

我们面临的是一个很典型的 BI 需求：业务方有一批销售订单数据，散落在几个源表里，希望做两件事——

1. **加工成干净的分析数据集**：把订单明细、客户信息、商品信息拼起来，算好销售额、订单数，过滤掉无效记录，形成一张可供分析的数据集。
2. **生成一个经营分析看板**：让销售负责人能按日期、区域、品类筛查看销售额、订单数、区域贡献、商品排行、客户结构。

传统做法是：在观远 BI 界面里手工建 ETL 流程、配字段、写 SQL、再手工拖图表做看板。这套流程我们熟，但有两个痛点：

- **重复劳动**：类似的 ETL 和看板，不同业务线要做很多遍。
- **口径容易错**：销售额到底怎么算、客户数怎么去重，不同人做出来的不一样。

正好这个时候，观远推出了 GuanCLI 工具套件，官方明确说"面向 AI Agent 和命令行环境"。我们当时的判断是：**如果能把 WorkBuddy 和这套工具连起来，用自然语言驱动，也许能把"手工拖拽"变成"描述需求 + 确认结果"。**

## 为什么选 GuanCLI 工具套件

我们先把官方文档读了一遍，搞清楚这套工具到底是什么。核心结论：

- **GuanCLI 是底座**：负责连接 BI 环境、管理登录认证、查询数据集/页面/卡片/ETL/任务等资源，还能预览数据、排查任务、操作表单、调用 ChatBI。
- **GuanVis 生成看板**：基于 GuanCLI 的认证与查询能力，让 AI 读数据集结构、自动生成并发布 BI 仪表板。
- **GuanETL 开发 ETL**：同样基于 GuanCLI 的认证，让 AI 打开、新建、修改、检查、预览、保存、运行和调度 ETL 流程。
- 还有 GuanDS（数据资产）、GuanMetric（指标资产），这次没用上。

一句话：**GuanCLI 负责"连接和查询"，GuanETL 负责"开发调试 ETL"，GuanVis 负责"生成看板"。** 这正好覆盖我们的两个需求。

还有一个关键点：GuanVis、GuanETL 都复用 GuanCLI 的登录状态，不单独管理认证。这意味着**只要把 WorkBuddy 和 GuanCLI 打通，后面几个工具都能用**。

## 两个绕不开的前提

在读文档时，我们注意到两条硬约束，直接影响了项目能不能做：

**第一，商业授权。** 官方文档写明，自 2026 年 9 月 1 日起，使用 GuanCLI、GuanVis、GuanETL 等都需要开通商业授权。这是前置条件，没有授权后面都免谈。我们确认了公司已有授权才继续。

**第二，环境要求。** 需要 Node.js V22 或更高版本。我们先用 `node -v` 和 `npm -v` 检查了环境。

这两条看起来是小事，但如果不提前确认，会在安装阶段卡住。这也是我们后面对团队强调的："先确认授权和环境，再动手。"

## WorkBuddy 在这个项目里的角色

这个项目里，WorkBuddy 不是"写代码的助手"，而是"调用工具的调度中枢"。具体承担四类工作：

1. **环境管家**：检查登录状态、切换环境、确认账号，避免连错环境。
2. **ETL 开发助手**：读 ETL 结构、改草稿、做检查、预览结果、汇报改动。
3. **看板生成助手**：读数据集结构、设计图表、生成页面、发布到测试目录。
4. **排错助手**：任务失败时查原因、给建议。

贯穿全程的原则只有一条：

> AI 负责"读、改、生成"，人负责"定口径、做确认、验结果"。凡是写入、发布、运行、调度、删除，都要人确认后才执行。

这条原则不是我们凭空定的，而是官方文档反复强调的。文档明确说：GuanVis、GuanETL 可以创建或修改 BI 资源，生产环境使用前要先让 AI 说明目标资源、影响范围和即将执行的操作，确认后再保存、发布、运行或删除。

## 环境搭建：先把底座装好

GuanCLI 工具套件的关系是"底座 + 上层工具"：GuanCLI 是底座，GuanETL、GuanVis 都依赖它的登录状态。所以安装顺序不能乱——先装 GuanCLI 并登录，再装上层工具。

### 第一步：检查并准备 Node.js

官方文档要求 Node.js V22 或更高。我们第一步就是检查：

```bash
node -v
npm -v
```

如果版本不够或找不到命令，要先装 Node.js。文档给了两种方式：手动下载安装，或者让 Agent 装。我们用了后者——直接把这句话发给 WorkBuddy：

```text
帮我安装 Node.js V22+
```

装完重新开终端，再 `node -v` 确认。这一步有个小坑：装完 Node.js 后旧终端窗口不会自动识别新环境，必须重开终端。

### 第二步：安装 GuanCLI 底座

```bash
# 首次安装
npm install -g @guandata/guancli

# 已安装过的更新
npm update -g @guandata/guancli

# 验证
guancli version
```

官方文档提到，如果安装成功但 `guancli version` 提示找不到命令，通常是 npm 全局命令目录没进 PATH。排查命令：

```bash
npm prefix -g
```

macOS/Linux 把 `$(npm prefix -g)/bin` 加进 PATH，Windows 把 `%AppData%\npm` 加进 PATH，然后重开终端。我们这台机器装完直接能用，没遇到这个问题，但这个排查思路记下来备用。

### 第三步：安装 Skill，让 AI 会用工具

这是关键一步。GuanCLI 除了命令行，还提供一套 **Skill**——给 AI 助手用的"工具使用说明"。官方说得很直白：**想让 AI 用自然语言操作 BI，必须安装 Skill**，否则 AI 不知道该调哪个命令。

```bash
guancli install-skill
```

装完之后，你对 WorkBuddy 说"帮我列一下当前 BI 环境的数据集目录"，它就知道该调 `guancli dataset list` 之类的命令。没装的话，它只能一脸茫然。

::: tip
Skill 是"说明书"，不是"认证"。它告诉 AI 怎么用工具，但不包含登录信息。登录还是得走 GuanCLI 的认证。
:::

### 第四步：登录 GuanCLI

```bash
guancli auth login
```

按提示依次输入：

1. **环境名称**：默认 `default`，也可以填 `prod`、`test`。给不同环境起不同名字，是为了本地存多份配置，后面能秒切。
2. **BI 系统 URL**：比如 `https://demo.guandata.com`。
3. **登录方式**：四种可选——浏览器 OIDC 登录（推荐）、用户名密码、直接输入 uIdToken、直接输入 PAT。
4. 如果选用户名密码，还要填 Domain（多租户/私有化部署用，一般用户回车留空）、Login ID、Password。

登录成功后，凭证自动存到本机，后续命令不用重复登录。

### 登录方式怎么选：我们踩过的坑

官方文档列了四种登录方式，我们实际试了几种，记录如下。

**账号密码登录**：最直观，适合交互式使用。我们测试环境用了这个。缺点是密码要输入，不适合自动化脚本。

**uIdToken 登录**：从浏览器 Cookie 里拿 `uIdToken`。官方文档特别提醒：**uIdToken 有效期较短，长期使用不建议**。我们一开始图省事用了这个，结果第二天就失效了，重新登录了一遍。教训：临时调试可以，长期用别选它。

**PAT 登录**：Personal Access Token，以 `gdpat_` 开头，支持单独配置权限和到期日期，更适合长期使用。这是官方推荐给自动化场景的方式。我们生产环境最后换成了 PAT。

非交互式配置（适合自动化）：

```bash
guancli auth login \
  --profile prod \
  --url https://bi.example.com \
  --pat '<你的令牌>' \
  --default
```

`--default` 可选，把该环境设为默认。

::: warning PAT 安全
官方文档对 PAT 安全有明确警告，我们也写进了团队规范：
- 不要把真实 PAT 写进 Markdown、Git 仓库、工单、聊天记录、截图或 CI 日志。
- 共享机器上优先用交互式登录。
- 非交互式命令可能进 Shell History，执行期间也可能被进程列表看到，只在可信环境用。
- 怀疑泄露立即在 BI 里吊销并重建。
:::

**浏览器 OIDC 登录**：文档推荐的方式。浏览器打开观远 BI 登录页，用户完成登录后 GuanCLI 拿到凭证，终端里不用输密码。适合不想在终端存密码的场景。但需要管理员提供 OIDC Client ID 和 Client Secret，配置成本略高。我们这次没用，但记下来了。

### 验证登录：别急着干活

登录完不要立刻开始改东西。先验证：

```bash
guancli auth status

guancli auth whoami

guancli bi info
```

这三个命令确认：当前登录的是哪个环境、账号是谁、BI 是否可访问。官方推荐的工作流第一步就是"先确认环境"，我们把它固化成了团队习惯。

如果用 PAT，还要额外验证：

```bash
guancli --profile prod server-version
guancli --profile prod ds tree
```

- `server-version` 成功，说明 PAT 能访问基础 API。
- `ds tree` 成功，说明 PAT 还有数据集读取权限。

这里有个细节值得记：官方说 `status` 显示"有效"但业务命令失败，通常表示 PAT 有效但缺少对应业务权限。我们遇到过一次——`status` 是 valid，但 `ds tree` 失败，最后发现是 PAT 没勾数据集权限，重新授权才解决。

### 多环境切换：test 和 prod 秒切

我们配了两套环境：测试用 `test`，生产用 `prod`。切换命令：

```bash
# 查看所有环境
guancli auth list

# 切换默认环境
guancli auth use prod
```

这个能力很重要。我们的工作流是：**所有操作先在 test 环境验证，确认无误后切到 prod 再执行**。切换只要一条命令，不用重新输 URL 和账号密码。

::: warning 永远先确认当前环境
GuanCLI 权限跟随当前登录用户，能看到什么、能做什么都取决于当前环境。`guancli auth use` 切环境很快，但也容易切错而不自知。我们的规矩是：每次执行写操作前，先跑一遍 `guancli auth status` 确认环境。
:::

### 安装上层工具：GuanETL 和 GuanVis

底座装好并登录后，再装两个上层工具：

```bash
# GuanETL
npm install -g @guandata/guanetl
guanetl install-skill
guanetl version

# GuanVis
npm install -g @guandata/guanvis
guanvis install-skill
guanvis version
```

注意每个工具都要单独 `install-skill`——这是给对应工具装"说明书"，让 AI 知道何时调用它。官方特别说明：这些 `install-skill` 不替代 GuanCLI 登录，操作 ETL/看板时仍复用 GuanCLI 的认证配置。

装完后，让 WorkBuddy 自检一遍：

```text
请帮我检查当前电脑是否已经安装 GuanCLI、GuanETL 和 GuanVis，
并确认当前已经登录观远环境。只做检查，不要修改任何 ETL 或看板。
```

它会确认几个工具是否可用、当前登录哪个环境、账号是谁。这一步相当于"开工前的点名"。

## 先探索再动手：用 GuanCLI 摸清数据

正式开发前，我们用 GuanCLI 做了一轮探索。这一步的价值是：**在写任何 ETL、生成任何看板之前，先搞清楚数据长什么样、口径是什么、谁在用**。

官方推荐的工作流是"先检查环境，再查询资源，最后执行高风险操作"。我们严格遵守了这个顺序。

### 搜索并理解数据集

业务方说"用销售订单数据"，但 BI 里可能有十几个名字带"销售"的数据集。我们先让 WorkBuddy 搜：

```bash
guancli ds search 销售
```

搜出来几个候选。然后针对目标数据集看结构：

```bash
guancli ds get <ds_id>
```

WorkBuddy 会把字段、类型、维度、度量、计算字段、血缘都读出来，整理成一张表。我们重点确认了几件事：

- 有没有日期字段，粒度是日还是月。
- 金额字段叫什么，是单价还是总价。
- 数量字段叫什么。
- 区域、品类、客户字段分别是哪个。
- 这个数据集是哪个 ETL 生成的（血缘）。

### 预览数据，验证口径

光看字段不够，要看真实数据。我们让 WorkBuddy 预览一批：

```bash
guancli ds preview <ds_id> \
  --filter "日期 toMonth EQ 2026-01" \
  --filter "城市 EQ 上海" \
  --sort-desc 销售额 \
  --limit 20
```

这个命令的要点：

- `--filter` 可以多次传，多个条件之间是"与"关系。
- 过滤语法是 `字段 操作符 值`，比如 `城市 EQ 上海`、`日期 toMonth EQ 2026-01`。
- `--sort-desc` 指定降序字段。
- `--limit` 限制返回行数。

我们让 WorkBuddy 用自然语言提这个需求："帮我看一下销售明细数据集里，2026 年 1 月上海的数据，按销售额倒序取前 20 行。"它自己翻译成了上面的命令。

这一步帮我们发现了一个大问题（后面踩坑章节详述）：**销售额字段到底是 `unit_price` 还是 `quantity * unit_price`？** 数据预览里看到的值和业务方说的不一致，这才引出后面的口径确认。

### 追溯数据集的上游 ETL

既然要改 ETL，得先知道现有 ETL 长什么样、输出给谁。我们用了血缘查询：

```bash
guancli ds get <ds_id> --assoc
guancli etl get <etl_id>
```

`--assoc` 会带出关联信息，能看到这个数据集是哪个 ETL 生成的。`etl get` 则看 ETL 的节点、SQL、输入输出、血缘。

WorkBuddy 把这些信息整理成一句话："这个销售汇总数据集由 ETL '销售订单清洗' 生成，上游是订单明细表 + 客户信息表，输出到数据集 '销售分析基底'，下游被 3 个页面引用。"

这句话非常关键——它直接告诉我们：**改这个 ETL 会影响 3 个下游页面**。所以后面所有修改都格外谨慎。

### 排查任务历史

我们还顺手查了一下最近的任务运行情况：

```bash
guancli task history --status Failed --task-types ETL_COMBINED
```

看到有几条失败记录。让 WorkBuddy 分析原因：

```bash
guancli task get <task_id>
guancli task detail <task_id>
```

它总结说大部分是上游数据源临时不可用导致的偶发失败，不是 ETL 逻辑问题。这个结论让我们放心——要改的是 ETL 逻辑，不需要处理历史失败任务。

### 探索阶段的产出

这一轮探索，我们得到了一份"作战地图"：

| 项目 | 结论 |
| --- | --- |
| 目标数据集 | 销售订单明细，字段已确认 |
| 销售额口径 | 存疑：需业务方确认（unit_price vs quantity×unit_price） |
| 现有 ETL | 销售订单清洗，输出到销售分析基底 |
| 下游影响 | 3 个页面引用，改动需谨慎 |
| 历史任务 | 偶发失败，非逻辑问题 |
| 环境 | test 环境，账号已确认 |

::: tip 为什么要先探索
如果跳过这步直接让 AI "帮我改 ETL"，它不知道要改哪个、口径是什么、影响谁，很可能改错或者漏掉下游。花在探索上的时间，后面会以"少返工"的形式还回来。这也是官方文档反复强调"先查询再操作"的原因。
:::

## ETL 开发：小步验证的七步法

ETL 开发是这次项目的重头戏。我们没有让 AI 一口气改完整个流程，而是按官方文档的"七步法"推进，每一步都先检查、再确认。这个节奏是项目能稳的关键。

### 为什么不敢一口气改完

GuanETL 能创建或修改 BI 资源，属于高风险操作。官方文档明确警告：涉及正式客户环境、生产目录或重要线上 ETL 时，要先确认字段口径、输出位置、下游依赖和影响范围。

我们面对的 ETL 有 3 个下游页面，改错了影响面不小。所以定了一个原则：**先小步、先测试、先检查，每个改动都要能回滚**。

### 第一步：检查工具和登录状态（只检查不改）

开工第一句话，只让 AI 检查，不许改：

```text
请帮我检查当前电脑是否已经安装 GuanCLI 和 GuanETL，
并确认当前是否已经登录观远环境。只做检查，不要修改任何 ETL。
```

AI 应该确认四件事：

- `guanetl` 是否可用
- `guancli` 是否可用
- 当前登录哪个观远环境
- 当前账号是谁

这一步的目的是"确认没连错环境"。我们当时是 test 环境，账号是个人测试账号，符合要求。

### 第二步：找一个低风险 ETL

官方文档建议首次试用选名称里带"测试"或"示例"的 ETL。我们没有直接拿"销售订单清洗"开刀，而是先找了个测试 ETL 练手：

```text
请帮我找一个名称里包含"测试"或"示例"的 ETL，
列出它的名称、ID、目录、输入数据和输出结果。先不要打开草稿，也不要修改。
```

我们先用测试 ETL 走通了"打开草稿 → 改一点 → 检查 → 预览 → 汇报"的完整闭环，确认工具链没问题，才切到真正的目标 ETL。这一步很多人会跳过，但我们觉得值——它把"工具会不会出问题"和"业务逻辑对不对"两件事分开了。

### 第三步：打开 ETL 草稿但不修改

确认目标 ETL 后，让 AI 打开草稿：

```text
请用 GuanETL 打开"销售订单清洗"这个 ETL，生成本地草稿。
打开后请告诉我草稿放在哪里、包含哪些文件，以及后续哪些文件可以改。先不要修改。
```

AI 打开后，会生成本地草稿目录。官方文档说明了草稿里哪些文件能改、哪些不能：

**可以改的（流程文件）：**
- `etl/etl.go`
- `etl/*.sql`
- 必要时 `etl/meta.json`

**不要手工改的（系统状态/导出产物）：**
- `_guanetl_state.json`
- `_input.json`
- `_base_etl.json`
- `_exported.json`

这个区分很重要。我们特意让 AI 把这两类文件列出来，团队里每个人都清楚"只能动 etl/ 目录下的流程文件"。

### 第四步：做一个小改动并先检查

这是最关键的一步。我们没有让 AI 大改，而是先做一个很小、容易验证的改动——过滤掉金额为空的订单：

```text
请在这个 ETL 草稿里做一个小改动：订单金额为空的数据不要进入最终结果。
改完后先检查配置和结果，暂时不要保存到线上。
请告诉我你改了什么、检查是否通过、结果是否符合预期。
```

注意话术里的三个"刹车"：

- "做一个小改动"——限定范围
- "先检查配置和结果"——要求检查
- "暂时不要保存到线上"——明确不改线上

AI 改完后，汇报了三件事：改了哪个 SQL 节点、加了什么过滤条件、检查结果通过、预览数据量符合预期。

**检查结果 0 行怎么办？** 官方文档专门提到这个问题。我们后来真遇到了一次：检查结果显示 0 行，但不一定是失败，可能只是筛选条件太严或源数据本身没匹配。处理办法是让 AI 继续查：

```text
检查结果是 0 行。请先看看源数据有没有数据，
再检查过滤条件、关联条件和字段类型。
```

### 第五步：确认后再保存

只有确认检查结果没问题，才让 AI 保存：

```text
检查结果我确认了。请保存到观远环境。
保存前再确认一次当前环境和目标 ETL，保存后告诉我是否成功。
```

官方特别强调"生产环境不建议跳过这一步确认"。我们即使是在 test 环境，也坚持了这一步——它形成了"AI 提议、人确认"的习惯，将来切到 prod 时不会变形。

### 保存失败的教训

我们遇到过一次保存失败。官方文档的建议是"先不要反复直接保存"，我们照做了：

```text
保存失败了。请不要直接重复保存。
先分析失败原因，如果可能是线上版本已经变化，
请重新打开最新版本，再做最小修改和检查。
```

原因最后查明：有人在我们改草稿期间动过线上 ETL，我们的草稿基于旧版本，保存时冲突。重新打开线上最新版本、做最小修改后保存成功。

教训：**草稿是基于打开那一刻的线上版本，协作场景下要注意版本变化。** 反复直接保存只会失败得更彻底。

### 第六步：运行并等待终态

保存成功后，要验证全链路运行：

```text
请运行刚才保存的 ETL，并等待任务结束。
如果失败，请告诉我真实错误信息和下一步排查建议。
```

这里有个大坑：官方明确说 **"已开始运行"不代表成功**，它只表示观远接受了运行请求，流程可能还在跑，也可能后面失败。所以必须等终态。正确的命令是：

```bash
guanetl run <etl_id> --wait --timeout 600
```

或者等已提交的任务：

```bash
guanetl task wait <taskId>
```

我们一开始没加 `--wait`，看到"已开始运行"就去干别的了，回来才发现任务早失败了。后来固化为"必须等终态"。

### 第七步：设置定时调度

ETL 要每天自动跑，用自然语言配调度：

```text
请把这个 ETL 设置为每天凌晨 3 点自动运行。
设置前先确认当前环境和目标 ETL，设置后用简单的话说明规则。
```

AI 设置后用大白话复述了一遍："已设置每天 03:00 自动运行，目标 ETL 是销售订单清洗，输出到销售分析基底数据集。"我们核对无误后确认。

### 删除前检查演练

官方还提到删除 ETL 的默认保护机制。我们做了一次演练（不是真删）：

```text
请帮我检查这个 ETL 能不能删除。只做删除前检查，
告诉我会影响哪些输出数据、有没有页面或其他流程还在使用它。不要直接删除。
```

AI 列出了下游依赖（就是那 3 个页面），说明"如果删除会导致这些页面无数据"。这正是我们要的——**高风险操作前先看影响范围**。真的要删时，命令是：

```bash
guanetl delete <etl_id>          # 默认先做删除前检查
guanetl delete <etl_id> --yes      # 确认后执行
guanetl delete <etl_id> --cascade --yes  # 连带删输出数据集，仅安全检查通过时
```

## ETL 阶段的成果

走完七步，我们得到：

- 一个"销售订单清洗" ETL：多表关联、字段加工、金额空值过滤，输出到"销售分析基底"数据集。
- 每天凌晨 3 点的定时调度。
- 一份完整的改动—检查—保存记录，谁改了什么、什么时候改的，清清楚楚。

更重要的是，我们验证了一套可复用的节奏：**检查 → 找低风险对象 → 打开草稿 → 小步改 → 检查 → 确认保存 → 等终态**。这套节奏后来成了团队标准。

## 看板生成：从自然语言到可发布页面

ETL 跑通后，数据有了，下一步是生成看板。这一步用 GuanVis。和 ETL 一样，它不是"一句话生成完美看板"，而是"描述需求 → 生成初稿 → 人工校验 → 迭代"的过程。

### 第一步：先让 AI 理解数据集

不要上来就说"做个看板"。先让 AI 读数据集，判断适合做什么分析：

```text
请查看"销售分析基底"这个数据集，说明它适合做哪些业务分析。
```

AI 读完后，会列出这个数据集有哪些字段——日期、金额、数量、区域、品类、商品、客户等，以及适合做哪些指标和图表。

这一步的价值是**对齐认知**：如果 AI 理解的数据结构和业务方说的不一样，现在就能发现，而不是等看板生成完才发现。

### 第二步：提出完整的生成需求

确认数据集适合后，提出完整需求。官方给了一个很好的需求模板，我们照着写：

```text
请基于"销售分析基底"数据集生成一个销售经营分析看板。

目标用户是销售负责人，重点查看本月销售额、订单数、区域贡献、
商品排行和客户结构。

销售额口径是 quantity * unit_price。

需要日期、区域、品类、订单状态筛选。

整体风格清晰克制，适合业务人员日常查看。

请先发布到测试目录。

生成后告诉我页面名称、页面 ID、主要图表，以及需要人工确认的指标口径。
```

这段话里有几个要素，缺一不可：

- **目标用户**：销售负责人——决定了详略和风格。
- **重点指标**：销售额、订单数、区域贡献、商品排行、客户结构——决定了图表。
- **口径**：销售额 = quantity × unit_price——这是最关键的一句，后面详述。
- **筛选维度**：日期、区域、品类、订单状态——决定了筛选器。
- **风格**：清晰克制——避免花哨。
- **发布位置**：测试目录——控制风险。
- **汇报要求**：页面名称、ID、图表、待确认口径——方便我们验收。

::: tip 为什么口径必须写进需求
"销售额"这个词，不同人理解不同：有人认为是单价 `unit_price`，有人认为是数量乘单价 `quantity * unit_price`，还有人要扣折扣、扣退款。如果不写清楚，AI 会按自己的理解选一个字段，生成出来的看板数字和业务方预期对不上。我们在 ETL 阶段就发现了这个问题（数据预览的值和业务方说的不一致），所以这次明确写进了口径。
:::

### 第三步：查看和反馈

生成完成后，进 BI 目标目录看页面。官方列了一个检查清单，我们逐项对照：

- 页面名称、页面 ID、发布目录是否符合预期
- 指标口径是否正确
- 字段选择是否符合业务含义
- 图表类型是否合适
- 筛选器是否覆盖常用维度
- 页面是否发布到正确环境和目录
- 布局和视觉是否适合使用场景

我们重点核了口径——把看板上的本月销售额，和用 SQL 直接查出来的数对了一遍，一致才放心。

### 迭代：用具体指令改

第一版看板有几个地方要改，我们用很具体的指令反馈：

```text
区域销售贡献图改成按省份展示。
```

```text
客户结构图改成按客户等级展示销售额占比。
```

```text
订单明细表里增加订单状态和支付方式。
```

这些指令的共同点是**具体到字段和图表**。不说"这个图不好"，而说"改成按省份展示"。AI 能准确执行。

### 版本管理：默认不覆盖

GuanVis 有个我们很喜欢的策略：**调整已发布的仪表板时，默认发布为新版本，不覆盖原页面**。官方说这是为了便于对比和回滚。

这意味着我们可以放心迭代——每一版都在，不满意可以回到上一版。只有当确实要覆盖时，才明确说：

```text
我确认要覆盖原仪表板，请复用原页面和卡片 ID 发布。
```

我们全程用了"发新版本"，没有覆盖。这在处理核心指标时特别有用——可以对比新旧版本的数字，确认改动有没有引入问题。

### 口径不对时怎么改

如果生成结果的字段或指标不对，直接告诉 AI 正确口径：

```text
销售额不是 unit_price，应该用 quantity * unit_price。
```

```text
客户数应该按 customer_id 去重计数。
```

```text
订单数应该按 order_id 去重计数。
```

官方特别提醒：涉及财务、利润、客户数、订单数等核心指标时，建议由业务或数据负责人确认口径。我们把这条写进了交付流程——**看板交付前，必须让业务负责人签字确认口径**。

### 看板阶段的成果

- 一个"销售经营分析看板"：5 个核心图表 + 4 个筛选器，发布在测试目录。
- 一份需求描述文档（就是那段完整提示词），作为后续迭代的依据。
- 一份口径确认记录，业务负责人签字。

官方建议"如果后续还要维护这张看板，保留本次需求描述和生成结果，便于继续迭代"。我们照做了——那段需求描述现在就存在看板项目的 README 里。

## WorkBuddy 协作复盘

做完后回头看，这个项目里 WorkBuddy 用得好的地方和不好的地方都很明显。

### 用得好的地方

**1. 把"读结构"的时间压缩了**

GuanCLI 的资源查询能力很强，但命令多、参数多。以前要查一个数据集的结构、血缘、下游，得翻文档找命令。现在直接说"帮我看一下销售汇总数据集是哪个 ETL 生成的，上游逻辑是什么"，WorkBuddy 自己组合 `ds search`、`ds get --assoc`、`etl get`，把结果整理成一句话。

这不只是省时间，更重要的是**降低了使用门槛**——不熟悉 GuanCLI 命令的人也能用自然语言查到想要的。

**2. 自然语言转命令很准**

像数据预览这种带过滤、排序、限行的命令，手写容易出错。WorkBuddy 把"2026 年 1 月上海的数据，按销售额倒序取前 20 行"准确翻译成了带多个 `--filter`、`--sort-desc`、`--limit` 的命令。这种转换它做得很稳。

**3. 风险刹车的执行到位**

我们最担心的就是 AI"自作主张"直接保存、发布、删除。实际下来，只要话术里明确"先不要保存""只做检查""先发布到测试目录"，它都严格遵守了。这可能既靠 Skill 的设计，也靠我们每次都把刹车写进需求。

**4. 排错给方向**

保存失败、运行失败、检查结果 0 行，这些情况它都能给出排查方向，而不是乱猜一个原因。比如保存失败那次，它提示"可能是线上版本已变化"，这个方向最后证明是对的。

### 用得不好的地方

**1. 口径问题它发现不了**

销售额口径的事，是我们在数据预览时人工发现的。AI 读到 `unit_price` 字段，就默认用它当销售额，不会意识到业务上应该是 `quantity * unit_price`。它不懂业务，这类问题只能人盯。

**2. "已开始运行"的误判**

我们一开始没强调等终态，AI 报告"已开始运行"就停了，导致没发现后续失败。虽然官方文档有提醒，但 AI 不会主动等你——要你在需求里明确"等待任务结束"。

**3. 环境切换的风险**

GuanCLI 切环境只要一条命令，AI 执行得很快，但快也意味着容易切错而不自知。有一次它误以为还在 test 环境，差点在 prod 上执行保存。后来我们固化了"写操作前先 `auth status`"的检查，才稳住。

**4. 需求写得含糊时，它不会追问**

如果只说"帮我做个看板"，它会按自己的理解生成一个，不会反问"目标用户是谁、口径是什么"。**AI 不追问，不是因为它懂，而是因为它默认按最常见的方式做。** 所以需求必须人写全。

### 我们的应对原则

总结成四条：

1. **需求写全**：目标、用户、指标、口径、筛选、发布位置，一条不能少。
2. **刹车明确**："只检查""不要保存""发布到测试目录"这类话必须写进需求。
3. **关键口径人定**：财务、客户数、订单数这类指标，业务方确认后再让 AI 生成。
4. **写前查环境**：任何保存、运行、发布、删除前，先 `guancli auth status`。

## 踩坑清单

把这次踩的坑集中列一下：

| 坑 | 现象 | 原因 | 解决 |
| --- | --- | --- | --- |
| uIdToken 第二天失效 | 登录后隔天要重新登 | uIdToken 有效期短 | 长期用改 PAT |
| 销售额口径错 | 看板数字和业务方对不上 | AI 默认用 unit_price | 需求里写明 quantity×unit_price |
| 保存失败 | 反复保存都失败 | 草稿基于旧版本，线上已变 | 重开最新版本做最小修改 |
| 检查结果 0 行 | 以为 ETL 失败 | 过滤太严或源数据为空 | 先查源数据、过滤条件、字段类型 |
| "已开始运行"就停 | 没发现后续失败 | 没等终态 | 用 `--wait` 或 `task wait` |
| 差点在 prod 保存 | 切环境后没确认 | 切环境太快不自知 | 写操作前查 auth status |
| 找不到 guancli 命令 | 装完不能用 | npm 全局目录没进 PATH | npm prefix -g 查并加 PATH |
| AI 没调用工具 | 它直接用通用方式处理 | 没装对应 Skill | 装 skill 并在需求里点名工具 |

## 可复用经验

### 1. 先装底座再装工具

GuanCLI 是底座，GuanETL/GuanVis 依赖它的登录。顺序错了会卡在认证上。记住三步：装 GuanCLI → `auth login` → 装上层工具并各自 `install-skill`。

### 2. 长期用 PAT，别用 uIdToken

uIdToken 有效期短，适合临时调试。长期或自动化场景用 PAT（`gdpat_` 开头），支持配权限和到期日。但注意 PAT 安全——不进 Git、不进日志、不进聊天记录。

### 3. 探索阶段不能省

改 ETL 前先搞清楚：数据长什么样、口径是什么、上游是谁、下游有谁。跳过这步，后面全是坑。用 GuanCLI 的 `search`/`get`/`preview`/`--assoc` 把地图画出来。

### 4. ETL 走小步七步法

检查 → 找低风险对象 → 打开草稿 → 小步改 → 检查 → 确认保存 → 等终态。每一步都要能停、能查、能回滚。不要指望一口气改完整个流程。

### 5. 看板需求写全七要素

目标、用户、重点指标、口径、筛选、风格、发布位置。少一个，AI 就会按自己的理解补，补的往往不对。

### 6. 核心口径必须人确认

涉及钱、客户数、订单数，不管 AI 生成得多漂亮，都要业务方确认口径后再交付。这是底线。

### 7. 高风险操作三件套

保存、运行、发布、调度、删除前：

- 先 `guancli auth status` 确认环境
- 让 AI 说明目标 ID、影响范围、即将执行的命令
- 人确认后再执行

### 8. 默认发新版本，不覆盖

看板迭代用新版本，便于对比和回滚。只有明确确认无风险时才覆盖原页面。

## 安全与边界

- 不在提示词、文档、聊天记录里粘贴账号密码、Token、客户隐私数据。
- 试点和演示用独立测试账号，不用高权限生产账号。
- 所有操作先在 test 环境验证，再切 prod。
- 表单更新、资源保存、页面发布、ETL 保存/运行/删除属于高风险操作，必须人确认。
- 商业授权是使用前提，先确认授权再投入。


## 深入理解工具套件：为什么这样分工

我们用了一段时间才真正理解 GuanCLI 工具套件的分工逻辑。把这个过程记下来，是因为"为什么这样分"比"分别是什么"更能指导使用。

### 一个底座，四个专用工具

官方文档把工具分成五类：GuanCLI（通用底座）、GuanVis（看板）、GuanETL（ETL）、GuanDS（数据资产）、GuanMetric（指标资产）。我们一开始觉得分成五个工具太碎，用起来会不会很麻烦。实际用下来发现，这种分法有它的道理：

- **认证只有一处**：所有工具复用 GuanCLI 的登录状态，不用每个工具单独登录。这消除了最麻烦的"多套凭证"问题。
- **能力边界清晰**：查资源用 GuanCLI，做看板用 GuanVis，改 ETL 用 GuanETL。AI 知道该调哪个，不容易混。
- **按需安装**：只需要看板就装 GuanVis，不需要把五个都装上。我们这次只装了三个。

### Skill 是关键一环

我们一开始低估了 Skill 的作用。以为装了工具，AI 自然会用。结果第一次让 WorkBuddy "帮我查一下销售数据集"，它并没有去调 GuanCLI，而是用通用方式回答了一段泛泛的建议。

后来才明白：**工具装好了，但 AI 不知道什么时候该用、命令怎么填。** Skill 就是补上这一环——它是给 AI 的"工具使用说明"，告诉 AI 在什么意图下调用哪个命令、参数怎么填。

装完 Skill 再问同样的问题，它立刻调了 `guancli ds search 销售`。这个对比让我们印象很深：**没有 Skill，工具等于没装。**

### 和 GuanMCP 的选择

官方文档还提到 GuanMCP，是给企业 AI 助手（豆包、企微插件、钉钉智能体等）通过 MCP 接入 BI 能力用的。我们评估了一下：

- 如果 AI 运行在本地或受控环境，能装命令行工具，优先用 GuanCLI 套件。
- 只有当 AI 助手无法安装或调用 GuanCLI，只能通过 MCP 接外部工具时，才用 GuanMCP。

我们是本地开发环境，能装 CLI，所以选了 GuanCLI 套件。这个判断标准记下来，以后有新场景能快速选。

## 登录方式深度对比

登录看着简单，但我们在这上面花了不少时间。把四种方式的对比记下来。

### 四种方式一览

| 方式 | 适用场景 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 浏览器 OIDC（推荐） | 交互式日常使用 | 终端不存密码，权限跟随用户 | 需管理员配 OIDC 应用 |
| 账号密码 | 交互式，简单环境 | 最直接 | 终端要输密码，不适合自动化 |
| uIdToken | 临时调试 | 获取快 | 有效期短，频繁失效 |
| PAT | 长期/自动化 | 可配权限和到期日 | 需保密，创建稍复杂 |

### 为什么最后选了 PAT

测试环境我们一开始用账号密码，能用，但每次新终端都要登录。后来试了 uIdToken，第二天就失效——官方明确说 uIdToken 有效期短。

最后生产环境换成 PAT。PAT 以 `gdpat_` 开头，支持单独配权限和到期日。非交互式配置适合我们的自动化场景：

```bash
guancli auth login \
  --profile prod \
  --url https://bi.example.com \
  --pat '<你的令牌>' \
  --default
```

但 PAT 的安全要求也最多。我们把官方的警告原样写进了团队规范：

- 不把真实 PAT 写进 Markdown、Git 仓库、工单、聊天记录、截图、CI 日志。
- 共享机器优先交互式登录。
- 非交互式命令可能进 Shell History，执行期也可能被进程列表看到，只在可信环境用。
- 怀疑泄露，立即在 BI 吊销旧 PAT 并创建新 PAT。

### 凭证过期的处理

官方对"登录凭证过期"给了分情况的处理，我们也验证了：

- 账号密码登录且保存了密码：工具会尝试自动重新登录。
- uIdToken 登录或没保存密码：需要重新 `guancli auth login`。
- PAT 过期：创建新 PAT 后重新登录。PAT 的到期日期和权限不能修改，只能重建。

这条对我们很有用——它意味着 PAT 到期不能续，只能换新的。我们把 PAT 到期日记进了团队日历，提前准备新 PAT，避免到期当天中断。

## ETL 字段加工实战细节

ETL 开发这章讲了流程，这里把字段加工的具体细节展开。这部分是"改草稿"的核心内容。

### 多表关联的注意事项

"销售订单清洗" ETL 的输入是订单明细表和客户信息表，通过客户 ID 关联。多表关联最容易出的问题是**关联后行数膨胀**——如果客户信息表里同一个客户有多条记录，关联后订单会被重复。

我们的处理是在草稿 SQL 里加去重：

```sql
-- 客户信息去重，取最新一条
WITH customer_dedup AS (
  SELECT customer_id, MAX(updated_at) AS latest
  FROM customer_info
  GROUP BY customer_id
)
SELECT o.*, c.region, c.customer_level
FROM order_detail o
JOIN customer_dedup d ON o.customer_id = d.customer_id
JOIN customer_info c ON c.customer_id = d.customer_id AND c.updated_at = d.latest
```

这段 SQL 是 WorkBuddy 根据"客户信息要去重、取最新"的需求生成的初稿，我们检查了去重逻辑才让它继续。

### 字段加工的类型问题

金额字段从源表读出来是字符串，要转成数值才能算。我们让 AI 在草稿里加转换：

```text
在草稿里加一个字段加工节点：把 order_amount 从字符串转成数值类型，
转换失败的记录过滤掉，并在结果里标注转换失败的条数。
```

AI 加完后，检查结果里显示有 12 条转换失败。我们没忽略这 12 条，而是让 AI 列出来看看——发现是源数据里有些金额带了千分位逗号（如 "1,234.00"），直接转数值会失败。于是又加了一步"去掉逗号再转"。

这个细节说明：**检查结果里任何异常数字都要追。** 12 条看着少，但如果不查，这 12 条订单的金额就丢了。

### 空值过滤的顺序

我们让 AI 加"金额为空的订单不进入结果"的过滤。它把过滤放在了关联之后、输出之前。这个顺序是对的：

- 如果放在关联之前，可能把"金额为空但关联后能补上"的记录也过滤掉。
- 放在最后，能对所有加工完的字段做统一判断。

我们没有干预这个顺序，但检查时特意确认了——因为过滤顺序是 ETL 里容易出错又不容易发现的地方。

### 输出前的验证

保存前，我们让 AI 做了一次输出验证：

```text
请对草稿做最终检查：
1. 输出数据集的字段是否齐全
2. 记录数是否合理（对比源表数量）
3. 金额合计是否和源表对得上
4. 空值过滤是否生效
暂时不要保存。
```

这四项检查是我们自己设计的——官方文档给了检查能力，但"检查什么"要业务方定。我们把业务的验收标准翻译成了这四条，让 AI 逐项验。

## 看板设计的细节

看板生成这章讲了流程，这里展开设计细节。

### 图表选型的思考

"销售经营分析看板"最终包含这些图表：

| 图表 | 展示内容 | 选择理由 |
| --- | --- | --- |
| 核心指标卡 | 本月销售额、订单数、客户数 | 一眼看到关键数字 |
| 趋势线图 | 销售额按日趋势 | 看变化节奏 |
| 区域贡献条形图 | 按省份的销售额 | 排名直观 |
| 商品排行表 | 销售额 Top 10 商品 | 明细可查 |
| 客户结构饼图 | 按客户等级的销售额占比 | 看结构 |

这些图表是 AI 根据"重点指标"生成的初稿。我们做了调整——比如区域贡献一开始是地图，我们改成了条形图，因为省份排名用条形图更清晰、加载更快。

### 筛选器的取舍

需求里写了四个筛选：日期、区域、品类、订单状态。AI 全加了。我们检查时发现筛选器太多会让页面显乱，但业务方确实都需要——最后保留全部，但调整了布局：把日期和区域放顶部（最常用），品类和订单状态放侧边（次常用）。

这个调整是人工做的，AI 不会主动考虑"使用频率决定布局"。

### 指标口径的反复确认

销售额口径我们确认了三遍：

1. ETL 阶段：数据预览发现值和业务方说的不一致。
2. 看板需求里：明确写 `quantity * unit_price`。
3. 看板生成后：把看板数字和 SQL 直查结果对账。

三遍确认后才放心。这不是冗余——口径错了，整个看板都白做。我们把这三遍写进了交付 checklist。

### 视觉风格的克制

需求里写了"清晰克制"。AI 生成的初稿其实有点花——用了渐变背景、多种强调色。我们让它改了：

```text
去掉渐变背景，改成纯白底。
强调色只用一种，图表配色统一。
```

最终风格干净，适合业务人员日常看。这个案例让我们体会到：**AI 的"美观"标准和业务场景的"合适"不是一回事**，要人工把关。

## 团队落地：从个人试用到标准流程

项目做完后，我们面临一个现实问题：怎么让团队其他人也用起来？个人能跑通不等于团队能复用。这部分记录我们的落地过程。

### 先解决"敢不敢用"

团队里对 AI 改 BI 资源有顾虑，这很正常。我们分三步打消顾虑：

1. **演示**：用测试 ETL 现场走一遍七步法，让大家看到每一步都有检查、有确认、能回滚。
2. **规则**：把"只在本 test 环境试""只改测试 ETL""写操作前查环境"三条写成硬规则。
3. **陪伴**：第一周让大家对着我们的提示词模板改，不裸写需求。

顾虑的核心是"怕改坏"。我们用的办法不是"保证不出错"，而是"让出错可发现、可回滚"——小步、检查、新版本、测试环境，这四样凑齐，风险可控。

### 沉淀三份资产

我们把项目成果整理成三份可复用资产：

1. **提示词模板库**：开工自检、探索数据集、ETL 小步改动、看板生成、删除前检查等模板（见附录 B）。
2. **环境配置说明**：怎么装、怎么登录、PAT 怎么配、环境怎么切。
3. **检查清单**：ETL 输出验证四项、看板交付口径确认、高风险操作三件套。

这三份东西放进团队知识库，新人照着做就能上手。我们把它当成这个项目最有价值的产出——比交付的那个看板更值钱。

### 约定操作红线

团队约定了几条红线，谁都不能破：

- 不用生产账号做试验。
- 核心 ETL 改动必须两人复核。
- 涉及财务、客户数、订单数的口径必须业务方确认。
- 删除操作必须先做删除前检查，且至少两人在场。
- 任何保存/发布/运行前必须 `auth status`。

这些红线不是限制效率，而是让团队敢放心用——边界清晰了，反而放得开。

## 几段真实的协作对话

把几段有代表性的对话放出来，展示"人和 AI 怎么配合"。

### 对话一：发现口径问题

```text
我：
帮我看一下销售明细数据集里，2026 年 1 月上海的数据，
按销售额倒序取前 20 行。

WorkBuddy：
[执行 guancli ds search / ds get / ds preview]
预览结果：1 月上海共 320 条订单，销售额字段 unit_price
取值多在 50–200 之间。

我：
等一下，这个 unit_price 是单价吧？业务上销售额应该是
数量乘单价。帮我确认一下数据集里有没有数量字段。

WorkBuddy：
[重新查看字段结构]
有一个 quantity 字段。unit_price 是单价，
销售额需要用 quantity * unit_price 计算，数据集里没有现成的销售额字段。

我：
明白了，那口径就是 quantity * unit_price。记下来。
```

这段对话的价值：AI 老老实实读了字段，没有自作主张把单价当销售额；人根据业务常识发现了问题。**AI 提供事实，人做业务判断**，配合得很顺。

### 对话二：保存失败

```text
我：
检查结果确认了，请保存到观远环境。

WorkBuddy：
保存失败，错误提示：流程版本冲突。

我：
不要反复保存。先分析失败原因。

WorkBuddy：
从错误看，线上 ETL 版本比草稿打开时的版本新，
可能是有人在此期间修改过。建议重新打开最新版本，
做最小修改后再保存。

我：
好，重新打开最新版本，只加金额空值过滤，再检查。

WorkBuddy：
[重新打开、最小修改、检查通过]
已保存成功。
```

这段展示了"别反复试、先分析原因"的处理方式。AI 给的方向准确。

### 对话三：看板口径修正

```text
我：
看板生成了，但我核对发现本月销售额比业务方给的数字小很多。

WorkBuddy：
可能原因：口径用了 unit_price 而非 quantity * unit_price。

我：
对，帮我改：销售额口径改为 quantity * unit_price，
客户数按 customer_id 去重，订单数按 order_id 去重。

WorkBuddy：
[修改后重新生成，发布新版本]
已发布新版本，页面 ID 不变。请用新版本核对。
```

这段里 AI 先给原因、人确认、再改、发新版本——整个过程可追溯、可回滚。

## 从对话里总结的方法

这三段对话有个共同模式：

1. **人给具体指令或提出疑问**，而不是泛泛的"帮我弄一下"。
2. **AI 给事实或方向**，而不是替人做业务判断。
3. **人确认后再继续**，关键节点不跳过。
4. **有问题先分析，不盲目重试**。

这个模式可以套到几乎所有 AI 协作场景。我们把这四条写进了团队规范的第一页。

## 延伸场景：ChatBI、洞察与表单操作

除了 ETL 和看板，GuanCLI 还有几个能力我们在项目后期也用上了。记录一下，展示这套工具的完整面。

### 用 ChatBI 快速问数

看板做完后，业务方经常临时问一些数字，比如"最近 30 天营业收入是多少"。这种问题不值得每次都改看板，用 ChatBI 问数更合适。

```text
用 ChatBI 的经营主题问一下最近 30 天营业收入是多少。
```

WorkBuddy 会执行：

```bash
guancli chatbi list-theme
guancli chatbi query --theme-name "经营主题" --message "最近30天营业收入是多少？"
```

ChatBI 的好处是"基于已有主题问数"——主题里的指标口径是提前配好的，不用每次重新定义。我们把销售场景的几个常用指标配成了 ChatBI 主题，业务方可以直接问。

还有一个洞察能力：

```text
用 ChatBI 的经营主题分析最近 30 天营业收入变化原因。
```

```bash
guancli chatbi insight \
  --theme-name "经营主题" \
  --message "分析最近30天营业收入变化原因"
```

它会给出变化原因分析。我们把这个用在了月度经营会上——比人工翻数据快得多。但有一条：**洞察结论只当参考，不当结论**。官方也提醒要确认数据范围、统计时间和指标口径。我们每次都核对一下再往汇报里放。

### 从洞察结论制作交付物

官方还提到一个有意思的能力：基于仪表板洞察或洞察 Agent 提问，生成洞察结论，再据此制作 HTML 页面、PPT 或 SuperApp。

```text
用线下零售综合业绩分析这个 Agent 分析一下 4 月份的浙江省业绩情况。
```

```text
基于洞察结论制作一个用于经营汇报的 HTML 页面。
```

我们试过一次，用它生成了一个汇报用的 HTML 页面。体验是：**结论生成快，但页面样式要人工调**。AI 生成的 HTML 布局比较通用，要符合公司的汇报风格还得改。这又验证了那个体会——AI 出初稿，人做打磨。

### 表单数据操作

另一个用到的能力是表单填报数据。我们有个"客户回访表"，需要查待处理记录并更新状态：

```text
帮我查一下客户回访表里状态为"待处理"的记录，
并把第一条改成"已处理"。
```

```bash
guancli form list 客户回访
guancli form schema <fmId>
guancli form query <fmId> --filter "状态 EQ 待处理" -f json
guancli form update <fmId> <rowId> --set "状态=已处理"
```

表单操作是写操作，风险高。官方特别提醒：**涉及写入、更新、删除表单数据时，先让 AI 展示即将操作的 `fmId`、`rowId` 和字段变更内容，确认后再执行**。我们严格执行了——AI 先列出要改哪条、改成什么，我们确认后才让它执行。

### 指标管理

GuanMetric 这次没深入用，但 GuanCLI 本身能查指标：

```bash
guancli metric search 销售额
guancli metric get <metric_id>
guancli metric query <metric_id> --dim 渠道 --limit 20
```

我们用它查过"销售额"指标的业务口径，确认它和看板里用的是同一套定义。这也是口径校验的一种手段——BI 里的指标定义和看板字段对得上，数字才可信。

## 风险控制的深入讨论

风险控制是这次项目最花心思的部分。这里系统展开。

### 风险分级

我们把所有操作按风险分了三级：

| 级别 | 操作 | 处理方式 |
| --- | --- | --- |
| 低风险 | 搜索资源、读结构、预览数据、查任务 | 可直接让 AI 执行 |
| 中风险 | 打开草稿、修改草稿、检查、预览结果 | 可让 AI 执行，但要汇报结果 |
| 高风险 | 保存、运行、发布、调度、删除、表单更新 | 必须人确认，先查环境 |

分级的好处是：**不用每件事都紧张，但高风险的一件都不放过**。低风险操作放开手让 AI 做，效率才上得来。

### "人确认"具体确认什么

"让 AI 说明影响范围后人确认"——确认什么？我们总结了四问：

1. **确认环境**：当前是哪个 profile？是 test 还是 prod？
2. **确认对象**：目标 ETL/看板的 ID 和名称对不对？
3. **确认变更**：具体改了什么字段、什么逻辑？
4. **确认影响**：下游有哪些资源？谁会受影响？

这四个问题答不上来，就不确认。AI 答不全，就让它补。

### 测试环境策略

我们的测试策略：

- 所有新操作先在 `test` profile 走一遍。
- 测试目录用个人目录，不影响别人的资源。
- 测试通过后，切 `prod` 环境，再走一遍同样的流程（但这次是真的）。
- 生产环境的写操作，必须有第二人在场复核。

这套策略让我们在 test 环境踩完了所有坑，到 prod 时基本一遍过。

### 回滚机制

"能回滚"是敢让人确认的前提。我们的回滚靠两样：

- **看板发新版本不覆盖**：不满意就切回旧版本。官方默认策略就是这样。
- **ETL 改动前记录原状态**：改草稿前先让 AI 说明当前配置是什么，万一要回退，照着恢复。

::: warning
ETL 的回滚比看板麻烦——它没有"版本切换"那么方便。所以我们对 ETL 的改动格外保守，坚持小步、每次只改一点、改完立刻检查。宁可多改几次，不要一次改错难回退。
:::

### 权限跟随用户

官方明确说：GuanCLI 调用 BI 时用当前登录用户或 Token 的权限，能看到什么、做什么取决于该用户在 BI 里的权限。

这意味着——**AI 不会给你超出你权限的能力**。它再强，也只能在你的权限范围内操作。这其实是个安全底线：我们用个人测试账号，AI 就只能动这个账号能动的资源，动不了别人的。

所以我们坚持"试点用独立测试账号"，这不只是为了不污染生产，也是为了把 AI 的能力锁在最小范围里。

## 如果重来一次，我们会怎么做

项目结束，想想哪些地方可以做得更好。

### 更早确认口径

销售额口径的问题是探索阶段发现的，但发现得有点晚——已经预览了好几批数据。如果重来，第一天就把业务方拉进来，把"销售额、订单数、客户数"这几个核心口径白纸黑字写清楚，再开始动 ETL。口径是源头，源头错了后面全错。

### 更早装 Skill

我们一开始没装 Skill，让 WorkBuddy 用通用方式回答了几个问题，浪费了时间。如果重来，装完工具第一件事就是 `install-skill`，然后立刻测一句自然语言，确认 AI 真的会调工具。

### 用 PAT 而不是 uIdToken

这个前面说过。如果重来，直接上 PAT，不在 uIdToken 上浪费时间。但要注意 PAT 到期日的管理，提前准备新 PAT。

### 把检查清单前置

输出验证的四项检查（字段齐全、记录数合理、金额对账、空值过滤）是开发中途才总结出来的。如果重来，开工第一天就写好这张清单，每个 ETL 都按它验。检查标准前置，比事后补更系统。

### 让更多人参与评审

这次主要是我们在做，业务方只在最后确认口径。如果重来，让业务方早点看探索结果的"作战地图"——数据长什么样、口径理解对不对——早对齐比晚返工强。

## ETL 节点与处理逻辑详解

GuanETL 生成的草稿里，`etl/etl.go` 和 `etl/*.sql` 是核心。这里把"销售订单清洗" ETL 的处理逻辑展开讲，展示一个 ETL 草稿实际长什么样、改了什么。

### ETL 的整体结构

这个 ETL 最终包含五个节点：

```text
输入节点（订单明细表）
    ↓
输入节点（客户信息表）
    ↓
SQL 加工节点（关联 + 去重 + 字段加工）
    ↓
过滤节点（空值过滤）
    ↓
输出节点（销售分析基底数据集）
```

WorkBuddy 打开草稿后，把这个结构画成图给我们看，让我们一眼看清数据流。这比读代码直观得多——这也是"先让 AI 读结构"的价值。

### SQL 加工节点做了什么

核心的 SQL 节点处理了四件事：

**1. 多表关联**：订单明细通过 `customer_id` 关联客户信息，带出区域和客户等级。

**2. 客户去重**：客户信息表有重复记录，用 `MAX(updated_at)` 取最新一条。

**3. 字段加工**：
- `order_amount` 从字符串转数值（先去千分位逗号）。
- 新增 `sales_amount` = `quantity * unit_price`。
- 日期字段从字符串转成日期类型。

**4. 口径统一**：把"销售额"统一成 `sales_amount` 字段，供下游看板使用。

这段 SQL 是 AI 根据我们描述的口径生成的。我们逐行看了，重点核对了去重逻辑和金额转换——这两处最容易出错。

### 过滤节点的位置变化

我们让 AI 加"金额为空不过滤"时，它一开始把过滤放在关联之前。我们检查时发现不对——有些订单金额为空，但关联后能从其他字段补算出来。于是让它把过滤移到 SQL 加工之后、输出之前。

```text
把空值过滤节点移到 SQL 加工节点之后，
对最终的 sales_amount 做判断，不要对原始 order_amount 做判断。
```

改完再检查，记录数比之前多了 12 条——正好是之前被误过滤的那批能补算的订单。这个细节让我们更加确信：**检查不只是看"通过没通过"，还要看"数字变化合不合理"。**

### 草稿文件里我们改了什么

最终改动的草稿文件：

- `etl/etl.sql`：加客户去重 CTE、金额转换、sales_amount 计算。
- `etl/etl.go`：调整节点顺序，把过滤节点后置。
- `etl/meta.json`：更新了输出字段说明。

没有动任何 `_` 开头的系统文件。这个边界我们守得很严——官方明确说那些是工具维护的状态文件，手工改会出问题。

## 看板生成原理与迭代

GuanVis 生成看板的过程，我们观察下来大致是这样：

### AI 做了什么

1. **读数据集结构**：调 `guancli ds get` 拿字段、类型、维度、度量。
2. **设计图表**：根据需求里的"重点指标"选图表类型。
3. **配筛选器**：根据"筛选维度"生成筛选器。
4. **生成页面**：创建页面和卡片，配置图表。
5. **发布**：发布到指定目录（测试目录）。

整个过程 WorkBuddy 会边做边汇报，比如"正在读取数据集 → 识别到 8 个字段 → 设计 5 个图表 → 生成页面 → 发布到测试目录"。这种过程透明让我们能随时叫停。

### 我们做了什么

- **写全需求**：七要素一条不少。
- **核对口径**：看板数字和 SQL 直查对账。
- **调整图表**：区域贡献从地图改条形图。
- **调整布局**：常用筛选放顶部。
- **确认发布**：确认目录、环境、版本。

### 迭代的节奏

看板改了三版：

| 版本 | 改动 | 结果 |
| --- | --- | --- |
| v1 | AI 初稿 | 图表齐全，但口径错（用了单价） |
| v2 | 修正口径 + 改区域图为条形图 | 数字对了，布局略乱 |
| v3 | 调整筛选器布局 + 统一配色 | 交付版 |

每一版都是新版本，没有覆盖。三版都在，随时能对比。这种迭代方式让我们很踏实——不怕改坏，因为改不"坏"已有的版本。

## 性能与使用体验

### 命令执行速度

GuanCLI 命令响应挺快。资源查询、数据预览都在秒级。ETL 运行要看数据量，我们的"销售订单清洗"跑一次大概几分钟，配了 `--wait` 等终态。

### 数据预览的 limit

`ds preview` 默认返回有限行，用 `--limit` 控制。我们一般先 `--limit 20` 看样例，确认结构后再决定要不要拉更多。一次性拉太多既慢又没必要。

### 大表格的处理

如果数据集很大，预览要加过滤条件缩小范围。我们用日期过滤（如 `--filter "日期 toMonth EQ 2026-01"`）先看一个月，确认没问题再看全量。这也是"先小后大"的思路。

把这套方案的架构画清楚，方便理解各部分关系：

```text
        ┌─────────────────────────────────┐
        │          WorkBuddy              │
        │   （调度中枢 · 自然语言入口）      │
        └──────────────┬──────────────────┘
                       │ 调用
        ┌──────────────▼──────────────────┐
        │           GuanCLI               │
        │  （底座 · 认证 · 查询 · 排查）     │
        └───┬──────────┬──────────┬────────┘
            │          │          │
       ┌────▼───┐ ┌────▼────┐ ┌───▼────┐
       │GuanETL │ │ GuanVis │ │ ChatBI │
       │开发ETL │ │生成看板 │ │ 问数   │
       └────┬───┘ └────┬────┘ └───┬────┘
            │          │          │
            └──────────┼──────────┘
                       │
              ┌────────▼────────┐
              │   观远 BI 平台    │
              │ 数据集/ETL/看板   │
              └─────────────────┘
```

关键点：

- WorkBuddy 是入口，人通过自然语言和它交互。
- GuanCLI 是底座，统一认证和查询。
- GuanETL / GuanVis / ChatBI 是上层能力，复用 GuanCLI 的登录。
- 所有操作最终落在观远 BI 平台上。
- 人的判断（口径、确认、验收）贯穿全程，不在图里的某一条线上，而在每个环节。

## 这套方案的适用边界

不是所有 BI 场景都适合这么做。我们总结了适用和不适用的情况：

**适合：**
- 需要快速搭建 ETL 初稿或看板初稿。
- 售前、实施、客户试用阶段要快速出成果。
- 有大量结构相似的重复工作（不同业务线的同类看板）。
- 团队有明确的口径和规范，只是执行环节想提效。

**不适合：**
- 口径本身还没定清楚、业务方没达成一致的场景。
- 高度敏感的财务、人事数据，不允许 AI 参与处理的。
- 没有商业授权，或环境不允许安装命令行工具的。
- 期望"一句话生成完美成品、完全不用人管"的——这种期待一定会失望。

认清楚边界，才知道什么时候用、什么时候别用。我们这个项目之所以顺利，很大程度上是因为需求属于"口径清楚、执行重复、初稿有价值"这一类。


## 交付规范：一份看板交付前要过哪些关

项目最后，我们整理了一份"看板交付规范"。这份规范现在团队每做一张看板都要过一遍。

### 交付前的五道关

1. **口径关**：核心指标（销售额、订单数、客户数）的口径已和业务方书面确认。
2. **数据关**：看板数字和 SQL 直查结果对账一致，数据量合理。
3. **结构关**：页面名称、ID、发布目录符合约定，图表类型合适。
4. **筛选关**：筛选器覆盖常用维度，布局符合使用频率。
5. **版本关**：发布的是新版本，旧版本保留可回滚。

五道关全过，才算交付。少一道都不发。

### 口径确认单

我们做了一个简单的口径确认单模板，业务方签字用：

```text
看板名称：[名称]
确认日期：[日期]

核心指标口径：
- 销售额 = [明确的计算方式]
- 订单数 = [是否去重、按什么去重]
- 客户数 = [是否去重、按什么去重]
- 统计时间范围 = [明确范围]

业务方确认：[签字]
数据负责人确认：[签字]
```

这张纸看着土，但它解决了大问题——口径争议时白纸黑字，不用扯皮。

### 交付物清单

一张看板交付时，我们同时交付：

- 看板本身（发布在 BI 指定目录）。
- 需求描述文档（生成看板时用的那段提示词）。
- 口径确认单。
- 数据来源说明（哪个 ETL、哪个数据集）。

这样后续维护的人能快速接手——知道看板怎么来的、口径是什么、数据从哪来。

## 常见错误深度解析

把几个最常见的错误现象展开讲，帮后来人快速定位。

### 错误一：找不到 guancli 命令

**现象**：`npm install -g @guandata/guancli` 成功，但执行 `guancli version` 提示找不到命令。

**原因**：npm 全局命令目录没进 PATH。

**排查**：

```bash
npm list -g @guandata/guancli   # 确认装了
npm prefix -g                    # 查全局目录
```

**解决**：把全局目录的 `bin` 子目录加进 PATH。macOS/Linux 是 `$(npm prefix -g)/bin`，Windows 是 `%AppData%\npm`。加完重开终端。

### 错误二：提示未登录或认证失败

**现象**：执行命令提示未登录。

**排查**：

```bash
guancli auth status   # 看状态
guancli auth login    # 重新登录
```

如果有多个环境，还要确认当前 profile 对不对：

```bash
guancli auth list
guancli auth use <环境名称>
```

### 错误三：登录凭证过期

**现象**：之前能用，突然提示凭证过期。

**处理**：

- 账号密码登录且存了密码：工具会尝试自动重登。
- uIdToken 或没存密码：重新 `guancli auth login`。
- PAT 过期：创建新 PAT 再登录（PAT 到期日和权限不能改）。

### 错误四：AI 没有自动使用工具

**现象**：让 WorkBuddy "改一下 ETL"，它没调 GuanETL，而是给了通用建议。

**原因**：没装 Skill，或需求里没点名工具。

**解决**：

```bash
guanetl install-skill
guanvis install-skill
```

需求里明确说："请使用 GuanETL 修改这个 ETL" 或 "请按 GuanVis 的方式生成看板"。

### 错误五：AI 找不到数据集

**现象**：说"用销售数据集"，AI 说找不到。

**原因**：环境不对、名称不全、数据集在别的目录、或没权限。

**解决**：让 AI 先确认环境再搜：

```text
请先确认当前 GuanCLI 登录环境，并搜索包含"销售"的数据集。
```

### 错误六：检查结果 0 行

**现象**：ETL 检查成功，但结果是 0 行。

**原因**：不一定失败，可能筛选太严或源数据为空。

**解决**：

```text
检查结果是 0 行。请先看看源数据有没有数据，
再检查过滤条件、关联条件和字段类型。
```

### 错误七：保存失败

**现象**：保存 ETL 反复失败。

**原因**：常见于草稿基于旧版本、线上已被改动。

**解决**：别反复直接保存。分析原因 → 检查配置 → 查是否复用旧工作目录 → 必要时重开线上最新版本，做最小修改再验证。

## 附录 C：常见问题 FAQ

**Q：GuanCLI 和 GuanVis/GuanETL 是什么关系？**

A：GuanCLI 是底座，负责连接和查询 BI；GuanVis、GuanETL 依赖它的登录状态，分别负责生成看板和开发 ETL。必须先装并登录 GuanCLI。

**Q：为什么装了工具，AI 还是不会用？**

A：因为没装 Skill。每个工具都要单独执行 `install-skill`，那是给 AI 的工具说明书。装完还可以在需求里点名"请使用 GuanVis/GuanETL"。

**Q：uIdToken 和 PAT 选哪个？**

A：临时调试用 uIdToken，长期使用或自动化用 PAT（`gdpat_` 开头）。PAT 支持配权限和到期日，但要注意保密。

**Q：怎么确认有没有连错环境？**

A：跑 `guancli auth status` 和 `guancli auth whoami`。写操作前养成习惯。

**Q：检查结果是 0 行，是不是失败了？**

A：不一定。先看源数据有没有数据，再查过滤条件、关联条件和字段类型。

**Q："已开始运行"是不是就成功了？**

A：不是。那只表示观远接受了请求。用 `guanetl run --wait` 或 `guanetl task wait` 等终态。

**Q：保存失败怎么办？**

A：别反复直接保存。先看失败原因，可能是草稿基于旧版本、线上已变。重开最新版本做最小修改再保存。

**Q：调整看板会覆盖原页面吗？**

A：默认不会，策略是发布新版本。确实要覆盖时，明确说"复用原页面和卡片 ID 发布"。

**Q：哪些文件能改？**

A：草稿里的 `etl/etl.go`、`etl/*.sql`、必要时 `etl/meta.json`。以 `_` 开头的 `_guanetl_state.json`、`_input.json` 等是系统文件，不要手工改。

## 小结

这次项目的核心体会是：**GuanCLI 工具套件把 BI 操作变成了"可被 AI 调用的能力"，但能不能用好，取决于人有没有把业务口径、风险边界、确认机制讲清楚。**

WorkBuddy 擅长的是"读结构、转命令、改草稿、生成页面"，不擅长的是"懂业务、定口径、做判断、控风险"。把前者交给它，后者留给人，这套分工跑下来是顺的。

如果你也在用 AI 做 BI 开发，希望这篇复盘里关于 ETL 七步法、看板需求七要素、口径校验和风险控制的记录，能帮你少走一些我们已经走过的弯路。
